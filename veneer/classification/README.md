# The resolution classification (WP-52)

Every symbol in WP-51's version map, sorted into one of four buckets by whether
the runtime has anything to stand behind it. This is the third quarter of the
libc veneer described in ROADMAP §10: WP-50 delivered the headers, WP-51 the
version map, and this decides, per symbol, how the map becomes a real
`libc.so.6` — which names WP-53 forwards, which it shims, and which it can only
stub. The classification is generated by matching the map against the runtime's
export surface rather than authored by hand, because a per-symbol table
maintained by hand would be wrong within a month, and because a generated
partition can be re-checked against its two inputs.

## The two inputs

The domain is `veneer/version-map/glibc-version-map.tsv` (WP-51): the 4024
symbol-to-node bindings el8's glibc exports across `libc.so.6` and eight
companions. The surface behind the veneer is `runtime/exports/cygwin-exports.tsv`
(WP-20): the outward face of `elfsysv1.dll`, generated from Cygwin's own
`cygwin.din`. A glibc symbol present on that surface under the same name is a
same-name forward; present under a reserved-name or large-file alias is a
forward under another name; present but semantically divergent is a shim; absent
is a stub. That is DR-0000's floor read one symbol at a time: the veneer is a
face over newlib plus Cygwin, so what Cygwin exports is what the face can carry.

## The four buckets, and a fifth disposition

    bucket           disposition     meaning
    1  forward-alias  forwards to a runtime export under another name
    2  forward-same   forwards to a runtime export of the same name
    3  shim           a runtime export exists but the semantics differ; a
                      translating wrapper is needed -- every such row is
                      flagged for review, never asserted final
    4  stub           nothing behind it; becomes a stub that fails predictably
       scaffold       a version-node identity object (a .dynsym entry whose name
                      is a version string, e.g. GLIBC_2.14); versioning scaffold
                      WP-53 regenerates from the node ladder, not an API provide

The fifth disposition, `scaffold`, is carved out rather than forced into a
bucket, and DR-0017 records why: a version anchor is not a function anyone calls,
and filing 68 of them under "stub that fails predictably" would corrupt the one
document the fourth bucket exists to be. The four functional buckets partition
every non-scaffold row; the reproduce test asserts all five dispositions cover
the map with nothing unclassified.

## How the buckets are decided

The rules are mechanical and applied in a fixed order, so the same inputs always
produce the same partition:

1. A name that is a version string (`GLIBC_*`, `XCRYPT_*`) is `scaffold`.
2. A name listed in `semantic-review.tsv` is a `shim`, flagged for review.
3. A name the runtime exports verbatim is a same-name forward.
4. A name that is a reserved-name alias of an export (`__X` over `X`, `_X` over
   `X`, `X` over `_X`/`__X`) is a forward under that name.
5. A large-file `X64` name whose base `X` is exported is a forward: on LP64 the
   64-bit variant aliases its base.
6. A `__*_chk` or `__*_finite` name whose base is exported is a `shim` over that
   base; if the base is also absent it is a `stub`.
7. Anything else is a `stub`.

Rules 1 through 5 and the `_chk`/`_finite` corner of 6 are decidable by name.
The rest of bucket 3 is not: whether a same-name export behaves as glibc's does
is a semantic question no name match can answer, so those calls are not guessed.
They are read from a curated file and flagged.

After the name rules, a second pass enforces the alias-strictness invariant
of the F2 redo (its decision record states it): no alias is classified less
strictly than its ultimate target. A forward whose target the map classifies
as a shim becomes a shim through the same translation — `open64` and
`__open64` carry the `O_*` flag translation `open` needs — and a forward of a stub
becomes a stub. The pass runs to a fixed point, so alias chains inherit the
strictness of the symbol at their end; 30 rows moved from bucket 1 to bucket 3
when it first ran, and none needed a written exemption.

## semantic-review.tsv

The review queue. Each row moves a symbol the name rules would call a forward
into bucket 3, because a runtime export exists but the Linux ABI the veneer must
present and the Cygwin ABI behind it disagree — on struct layout (`stat`,
`dirent`, `jmp_buf`, `sigaction`), on constant values (`O_*`, `F_*`, `RLIMIT_*`,
signal numbers), or on `errno`'s numeric values, which DR-0000 calls out by name.
Every entry is flagged for review, not an asserted shim design; a human confirms
the divergence and the wrapper before WP-53 emits it. The list is a first-pass
seed grounded in those divergence classes, not exhaustive, and expected to grow
as WP-53 implementation surfaces more. The generator fails if the queue names a
symbol the map does not contain, so it cannot drift out of sync with the map.

## The files

`classify.py` is the generator. `semantic-review.tsv` is the human review queue
it overlays. `classification.tsv` is the committed partition, one row per map
row. `bucket4-inventory.tsv` is the categorized fourth bucket the published
document reads. `t/reproduce.sh` is the certification.

## The format

`classification.tsv`, tab-separated, no header, in the map's own row order:

    soname   symbol   version   bucket   disposition   target   flag   reason

`bucket` is `1`, `2`, `3`, `4` or `scaffold`; `disposition` is its name;
`target` is the runtime export the symbol resolves to, or `-`; `flag` is
`review` for every shim and `-` otherwise; `reason` is the one-line rationale.

## Regenerating and testing

    ./classify.py -o classification.tsv --bucket4 bucket4-inventory.tsv    # regenerate
    ./classify.py --summary >/dev/null                                     # counts
    bash t/reproduce.sh                                                     # certify

`t/reproduce.sh` reruns the generator, diffs its output against the committed
`classification.tsv` and `bucket4-inventory.tsv`, asserts the partition covers
the map one-to-one with no symbol unclassified and none invented, checks that
every shim carries the review flag, asserts zero alias-strictness violations
from the committed file alone, and confirms `doc/what-the-veneer-lacks.md`
still states the generated counts. It exits 0 on success, 1 on any difference,
and 77 when there is no `python3`.

## Not decided here

- Whether each same-name forward in buckets 1 and 2 is truly semantically
  identical. This pass trusts the name; the review queue holds the divergences
  found so far, and more will surface when WP-53 implements against them.
- The shim designs themselves. Bucket 3 says a wrapper is needed and why, not
  what it is. That is WP-53's work, informed by the flagged reasons.
- Whether `libcrypt.so.1`'s `XCRYPT_2.0` node is ultimately provided. It is
  carried as `scaffold` like the GLIBC nodes; the WP-53/WP-54 scope call in
  DR-0013 is unchanged by this classification.
