# DR-0009 -- the down-call wrapper is a signature-agnostic ms_abi tail jump

Status: accepted
Date: 2026-08-30
Deciding: WP-21's implementer; a defensible call, not one of the reserved three
Proposal: none; taken while building WP-21's generated wrappers

## What was decided

Each down-call wrapper is one `ms_abi` function whose whole body is a tail jump
through the import's address slot:

    __attribute__((ms_abi)) void w_NtClose(void)
    { __asm__ __volatile__ ("jmp *%0" : : "m"(__imp_NtClose)); }

The System V to Microsoft argument translation happens at the caller's site,
emitted by the compiler from the `ms_abi` prototype the caller declares, not
inside the wrapper. The wrapper repacks nothing, so it is correct for any arity
and any argument types without the generator knowing the signature. This is
what lets WP-21 generate one wrapper per import mechanically from the import
list, which is the package's whole point.

## Why this and not a translating wrapper

The alternative is a wrapper that itself receives a System V call, is written
with the function's real prototype, and lets the compiler translate to MS ABI
inside it before calling the import. That keeps every byte of MS-ABI call
sequence inside the wrapper unit, which is a marginally stronger boundary. It
also requires the real prototype of all 370 imports at generation time, and the
prototypes are not in the import table; deriving them means parsing the Windows
headers for `ntdll` and `kernel32`, and getting one wrong -- an argument count,
a by-value struct -- miscompiles a real call silently. That is a large surface
to hand-verify against the project's own rule that a claim is anchored to
source at a ref, and none of it is WP-21's actual job, which is to make the
boundary explicit and mechanical.

The tail jump moves the one thing that genuinely needs the signature -- the
argument shuffle -- to the one place that genuinely has it: the call site,
where WP-22 writes the typed prototype as it consumes each import. The wrapper
keeps only what is signature-free: the indirection through the import slot and
the single named symbol that makes the audit possible. The split is clean along
the line of what each package knows.

The boundary the tail jump gives up -- MS-ABI call code appearing at System V
call sites rather than only in the wrapper unit -- is not the boundary the
done-condition asks for. That condition is about symbol references: no System
V-side object may name a raw import. The audit reads exactly that, and the tail
jump satisfies it, because every object but the wrappers unit names `w_<Name>`
and never `__imp_<Name>`.

## What it does not decide

The typed prototypes. Each wrapper's real return type and arguments are
declared by WP-22 at the call site as it uses the import; this record fixes the
wrapper's shape, not its callers' declarations.

The variadic surface. A variadic import cannot use this wrapper -- the tail
jump forwards a register and stack state the compiler already got wrong at a
cross-ABI variadic call site -- so the generator refuses one and routes it to
WP-24. Today none is imported, so the refusal never fires; the decision that a
variadic down-call is WP-24's, not a generated wrapper's, is recorded here but
owned there.

## What it costs to reverse

Moderate. The wrappers are regenerated by `gen-wrappers.sh`, so changing their
shape is one edit to the generator and one rerun. What a reversal touches beyond
that is WP-22's call sites: a translating wrapper would let callers use plain
System V prototypes, so switching to it after WP-22 has written `ms_abi`
prototypes against these wrappers means revising each. That coupling is why the
convention is settled now, before WP-22 depends on it.

Reversal is a new record pointing back here, not an edit to this one.
