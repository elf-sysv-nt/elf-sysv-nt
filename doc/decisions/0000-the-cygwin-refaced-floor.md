# DR-0000 — the floor is Cygwin re-faced, and el8's userland builds unchanged above it

Status: accepted
Date: taken at project inception 2026-08-20; recorded 2026-08-30
Deciding: the operator
Proposal: none. This is the premise the project was founded on. It is written
down now because it was questioned twice in one session and found asserted only
in passing prose, nowhere a reader could be pointed to.

## What was decided

The platform is Cygwin, re-faced: ELF and the System V AMD64 ABI presented
outward, Windows NT reached inward, by re-facing the one DLL every Cygwin host
call already funnels through rather than replacing what is behind it. The
purpose, and the measure of success, is that a Linux userland — el8's roughly
2900 source packages — builds against this platform unchanged, with its object
format, its symbol versioning, and its loader semantics intact.

The libc floor those packages link against is supplied by the platform: the
loader, `elfsysv1.dll`, and a libc veneer that exports glibc 2.28's versioned
ABI. That veneer is a face over newlib plus Cygwin. It is not el8's glibc.

## Why the C library is a face, not el8's glibc

Because glibc cannot run here, and the reason is measured rather than argued.
glibc's compiled code reaches every thread through `%fs` — the thread pointer at
`%fs:0`, initial- and local-exec TLS as literal `%fs`-relative instructions,
`errno` and locale through the same segment — and spike 1 established that a
`%fs` base does not survive a context switch on this Windows, with the loss
occurring in the scheduler no matter who set the base. Those are hardware
segment accesses baked into glibc's object code, not system calls a personality
layer could intercept, so no amount of Linux-syscall emulation underneath makes
them work. It is the same wall that forced DR-0003 to a `%gs` carrier and the
same one WP-12 answers by refusing `%fs` relocations at link time. Running el8's
glibc unchanged over a Linux-kernel personality is therefore not a harder
version of this project; it is a different and impossible one on this host.

glibc is not userland in any case. It is the floor. The packages above it do not
build on top of a pristine el8 glibc — the platform fills glibc's role,
ABI-identically, so the packages cannot tell the difference. That substitution
is what lets everything above it stay unchanged.

## The copy line

Above the floor, el8's files are used unchanged. The packages build pristine, and
the headers they compile against are el8's `glibc-headers-2.28`, vendored
verbatim — copying them is what commits the runtime to presenting Linux's ABI
exactly (errno values, signal numbers, struct layouts) and translating up from
Cygwin, which is the real work and belongs in the face rather than in anyone's
headers. A varied file above the floor is an exception that carries a written
reason and is expected to be rare: a package with a literal host-triple test, or
hand-written assembly that assumes a red zone. Copy is the default; the burden of
justification falls on variance, and on the honest inventory of what the face
does not provide.

## The runtime body is Cygwin compiled unchanged

The face is written or generated by construction — the loader against Cygwin's
`mmap`, the version matcher from Drepper's specification, the export and import
surfaces generated from Cygwin's own `cygwin.din` and import table. But the body
of `elfsysv1.dll` is not rewritten. It is Cygwin's `winsup/cygwin` source at the
DR-0007 ref, compiled unchanged, with the System V export face and the `ms_abi`
wrapping added around it; its entry points — `DllMain`, thread entry, the signal
path — are re-faced, not reimplemented. Writing a fresh Cygwin would violate this
record as surely as re-authoring a header does.

## What this does not decide

The per-package mechanics of each veneer symbol (forward, shim, or stub) are
WP-52's; the loader's and runtime's internal design are their WPs'. This record
fixes the floor and the copy line, not the work above them.

## Reversing this is a different project

Not a decision undone by a later record, but a different program of work: a
Linux-kernel personality on NT with el8's real glibc on top. It is foreclosed on
this host by the `%fs` measurement, and it discards the reason the project chose
Cygwin — that one DLL already funnels every host call — in favour of
re-implementing a kernel. Reopening it would mean beginning again, not amending
here.

## When to reopen

Only if the host itself changes: a Windows that preserves a user-written `%fs`
base across a context switch, together with a decision to pursue el8 glibc
unchanged for its own sake. Absent both, this record stands.

## What it corrects

DR-0010's framing. A record deliberating whether the veneer's `features.h` was
"copied" or "paraphrased" was already off the line drawn here — copying is the
rule, and the header is el8's. That decision is reframed by this one: the
question was never how faithfully to re-author the header, but that it should not
be re-authored at all.
