# DR-0028 — the low window is reserved by the parent, into a suspended stub

Status: accepted  ·  ratified 2026-08-30 (DR-0036)
Date: 2026-08-30
Deciding: the loader track, WP-41

## Context

A non-PIE ELF image is linked at a fixed address and there is exactly one place
it can be mapped. Every x86-64 toolchain this project cares about links one at
`0x400000`. Windows satisfies an allocation that names no base out of the lowest
free region, so every allocation a process makes before that address range is
held is an allocation made out of where the image has to go.

Spike 2 measured this on 2026-08-29 and it is what moved one word in the design
from decoration to requirement: a 4 MB span at `0x400000` was refused twenty
times in twenty from inside a running Cygwin process, while the same image at
`0x10000000` was accepted. The spike could not say where the reservation
therefore belongs, and named two candidates for this package to measure first: a
PE TLS callback, and the image entry point.

## What was decided

Neither candidate. The window is reserved by the parent, through
`VirtualAllocEx`, into a child created with `CREATE_SUSPENDED`, before the
child's first instruction runs; the child adopts what it finds. The stub is
linked with a stack reserve of `0x100000` rather than the toolchain's default
`0x200000`.

The window itself is `0x400000` for `0x3FC00000`: from the address every
non-PIE image is linked at up to the gigabyte boundary, which covers the image,
its brk, and the region a loader would choose for a shared object it wants near
the executable. Above that the ELF world is content to be placed wherever there
is room.

A Windows reservation cannot be partially released — the unit of `MEM_RELEASE`
is the whole allocation — so the window cannot be carved. It is handed over by
releasing it, placing the image while the address space is bare, and
re-reserving the two remainders. Nothing may allocate between the release and
the placement, which is a contract the caller keeps rather than something the
code can enforce.

## Why, and what was given up

The measurement is in `loader/exec/t/when-2026-08-30.txt` and is regenerated by
`loader/exec/t/reserve-when.sh`. Four routes were built from one source and each
was asked for the same block of numbers.

Arming from `main` was refused, which reproduces spike 2 and is the control.
Arming from a `.CRT$XLB` TLS callback does not link at all on this toolchain:
Cygwin's runtime supplies no `_tls_used`, so the image carries no TLS directory
and there is no callback slot to put a hook in. Arming from a replacement image
entry point — the earliest instruction the image owns — was refused too, and the
transcript says why: the initial thread's stack was sitting at `0x400000`,
placed there by the kernel while the process was being created, before any
instruction of the image ran. Below that address the survey shows the region
already chewed into small mappings by `cygwin1.dll`'s own initialization, which
also runs before the image entry point. There is no instant inside the image
early enough, and the two candidates the plan named are both refuted rather than
merely unproven.

Reserving from the parent into a suspended child succeeded, and the full
`0x3FC00000` window was found intact at the child's entry point. The fifth case
is the control for the fourth: the same reservation against a child built with
the default stack reserve is refused every time, because the kernel had already
placed that child's two-megabyte stack in the window. That is why the stack
reserve is part of this decision and not a tuning knob. It is also the one thing
the parent cannot arrange from outside, since the stack exists before the
process handle does.

What is given up is that the stub can no longer be started by hand and work. It
has a `--self-window` option that tries to reserve for itself, which normally
fails, and failing visibly is the point: a stub with no window refuses rather
than mapping the image somewhere else and producing a program that runs until
something reads an absolute address.

The release-and-replace handover is the weakest part. A cleaner mechanism exists
— `VirtualAlloc2` with `MEM_RESERVE_PLACEHOLDER`, split with
`MEM_PRESERVE_PLACEHOLDER` and filled with `MEM_REPLACE_PLACEHOLDER` — which
would let the window be carved without ever being released. Adopting it means
changing WP-32's mapper to allocate into a placeholder, which is a change to a
delivered package for a window measured in microseconds on a thread that is the
only one running. It is the right refinement and it is not this package's.

## Not verified

The window is released and re-reserved on the loader's own thread before any
other thread exists in the stub, which is why nothing is expected to allocate in
the gap. That expectation is reasoned rather than measured: no test injects an
allocation between the release and the placement, and none proves that the
Cygwin DLL has no timer or worker thread of its own running by then.

The measurement was taken on one host, on one Windows build, three times with
the same result. The stack placement it turns on is a kernel policy with
randomization in it, and a host that placed the initial stack elsewhere would
change which cases pass without changing what the decision should be. The script
is kept so the numbers can be retaken rather than believed.

`0x3FC00000` is a judgment about how much room the ELF world wants low, not a
measurement of how much it needs. Nothing yet allocates a brk or places a shared
object near the executable, so the first package that does may find the figure
too small or needlessly large.
